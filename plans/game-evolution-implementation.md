### Storage errors and competing tabs

Browser storage is scoped to an origin, which includes the site’s port. Keep the existing launcher origin stable and explain in README that another browser, private browsing, clearing site data, or changing the origin may make the slot unavailable. Don’t promise account/cloud recovery.

Perform the record read, expected-record comparison, and replacement write inside one IndexedDB `readwrite` transaction over `walks`. Overlapping read/write transactions on that store are serialized by the database. Compare the exact current JSON string with the session’s last committed observed string, including its revision. Missing-record authorization compares against absence. Invalid-record replacement compares against the exact string the player approved replacing. A mismatch aborts the write and latches the conflict, suppressing autosaves until an explicit load or newly confirmed walk restores authority. Use the surface-specific conflict copy below. Never overwrite the newer record or relabel the failed write “Saved.”

Prepare and validate the immutable JSON payload before opening the transaction. In the record-read success callback, recheck the active session generation and normal-mode/replacement authority before queuing `put`. Don’t await UI, audio, a timer, network, art, or animation inside a transaction. Listen for `complete`, `abort`, and `error`. Keep at most one in-flight transaction and one pending latest checkpoint. Update the expected record only after a successful complete, so a coalesced request from the same walk uses its own preceding committed revision.

Restart, scene replacement, and disposal invalidate pending requests and abort an uncommitted transaction when possible. Recheck generation before every queued write. An intentional `abort()` throwing `InvalidStateError` means the transaction may already be committing/finished, not that storage failed. Consume its existing terminal event or wait for it before the next replacement confirmation or Return. While the connection generation remains valid, a legitimate old normal transaction’s complete event may refresh the controller’s known committed snapshot for Return, but may not change the replacement game, its expected record, or its status. A new normal session adopts its own expected record only when explicitly loaded/committed. Before offering a replacement confirmation, settle/cancel the old transaction and reread the slot. Don’t use a cross-tab message as the write guard or assume a localStorage read/compare/write is atomic. The exception distinction follows the [transaction abort algorithm](https://w3c.github.io/IndexedDB/#dom-idbtransaction-abort).

Open database version 1 without deleting or resetting existing databases. Create `walks` only on initial creation. Handle open/read errors, blocked opening, unsupported newer database or payload versions, missing APIs, invalid JSON, aborted transactions, and quota failures while preserving play and existing records. Close the connection on `versionchange` or disposal. Unsupported/invalid string content remains untouched until an explicit replacement is confirmed against the current record. Non-string content follows the preservation rule below. No automatic migration, database deletion, clear-all operation, or fallback store is included.

### Database disconnect boundary

Give the save controller one idempotent storage-failure transition. Catch synchronous exceptions around IndexedDB access, `open`, `transaction`, `objectStore`, `get`, `put`, and best-effort `abort`/`close`, including calls inside request callbacks. Apply the intentional-abort exception distinction above before classifying a failure. Route asynchronous request/transaction errors and rejected storage promises through the same boundary. Save calls from `main.js`, especially a completed-action callback inside `animate()`, must return without throwing and must not produce an unhandled rejection. Keep the catch boundary around persistence, not unrelated game or rendering code.

On an unexpected database `close`, or on `versionchange` before explicitly closing, immediately mark storage unavailable and invalidate the storage-operation generation. Drop the pending checkpoint and best-effort abort the uncommitted transaction, then close/release the connection. Enter `unsaved` from `normal` without resetting the game, inventory, current action, quiz, language, sound intent, or overlay. An unclaimed title stays unclaimed; a study remains study. Clear Continue/Return and use the surface-specific status below. Cancel a pending Return as well as any saved-replacement flow, settle its waiting result, invalidate its completion handler, and release its busy state. Restore ordinary controls; unavailable Return stays hidden. Return leaves the current study/game and preferences intact with the correct failure status; it cannot load from a lost connection. A canceled saved replacement restores its prior panel and shows the failure panel above. Starting an unsaved replacement needs a new explicit choice. In-flight callbacks from the old connection cannot enqueue work, advance known/expected records, reenable saving, replace the game, or change status. A prior committed checkpoint is legitimate, but do not infer a failed operation saved anything.

Use the same stop-saving behavior for a synchronous storage exception, quota failure, or unexpected transaction abort. Intentional aborts for cancellation, a scene change, or a confirmed comparison mismatch carry their own reason and must not be misreported as database failure. Only an observed expected-record mismatch gets the competing-tab message. The first terminal cause wins for an operation, so the mismatch’s subsequent abort event cannot replace its conflict message with the generic failure message. A later genuine connection loss still makes storage unavailable. Disposal invalidates callbacks and closes silently; it must not redraw a disposed application.

Do not automatically reopen, retry queued writes, reconstruct a deleted slot from memory, or fall back to another store after storage becomes unavailable. Keep playing in memory and retain the failure warning. New walk can start another unsaved walk under the rules above. Reload is the only way to open storage again, and the warning must say unsaved progress will be lost. The app never calls `deleteDatabase` or clears the store as recovery. A blocked/failed initial open is settled as unavailable; close and ignore any late successful connection. A non-string existing value is unsupported and preserved: disable Continue and saved replacement for that value, and offer an unsaved walk. Do not invent an exact-string comparison for an unsupported object value.

The browser’s `close` event reports abnormal closure and is not fired by an explicit `db.close()`. Therefore `versionchange` must invoke the failure transition directly before closing. Creating a transaction on a closing/closed connection can throw synchronously. Those API facts are documented in the [IndexedDB connection-closing algorithm](https://w3c.github.io/IndexedDB/#closing-connection) and [transaction creation algorithm](https://w3c.github.io/IndexedDB/#dom-idbdatabase-transaction). The page must continue requesting animation frames and accepting ordinary input after either boundary fails.

Use these exact status variants. Match study first for prepared scenes, then finished status for normal/unsaved endings, then live-walk status. A new unsaved start uses its own row rather than carrying title copy into play. A storage reason is distinct from the normal/study/unsaved game mode, so a voluntary unsaved walk never reports a failed write.

| Surface and cause | Status |
| --- | --- |
| Unclaimed title, failed open or connection lost | “Saving is unavailable. Reload to check for a saved walk, or start a new walk without saving.” Hide Continue and offer Reload and New walk. Never claim the saved record was deleted. |
| Live normal walk, storage fails | “Progress couldn’t be saved. Closing the tab will lose unsaved progress. Keep it open to finish the walk.” |

| Finished voluntarily unsaved walk, no storage failure | “The finished walk isn’t saved. Keep the tab open to revisit the ending. Reloading loses unsaved progress.” |
| Study, storage fails | Keep “Scene study. Progress here isn’t saved.” Add “Saving is unavailable. Reload to check for a saved walk. Reloading will replace the study scene.” |
| Unclaimed title, comparison conflict | “Another tab saved a different walk. Reload to check it, start a new walk, or play without saving.” Hide old Continue; the failure panel offers Play without saving and Back. After Back, Reload, New walk, and Play without saving remain available while the conflict is latched. |
| Finished ending, comparison conflict | “Another tab saved a different walk. Start a new walk, or play without saving.” Keep the finished scene and expose the failure panel. After Back, Play without saving remains beside Walk again while the conflict is latched. |

Don’t promise recovery after site data is cleared, an operating-system crash, or power loss. Closing/reloading an unsaved walk loses its unsaved progress, regardless of whether saving failed or was voluntarily disabled.
